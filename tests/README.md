# AgentBridge regression tests

Run the complete suite with `npm test`. The runner first type-checks the test TypeScript, bundles the tests into a random system temporary directory with the repository's existing esbuild dependency, and executes them with `node:test`. On Windows it then copies the current workspace state (including uncommitted changes) to a second random system temporary directory while excluding `.git`, `node_modules`, the existing `dist`, VSIX files, and temporary artifacts; the copy reuses the workspace's already-installed dependencies through a local junction, runs the existing `build.mjs` there, packages that freshly built copy with the locally installed pinned `@vscode/vsce` binary, and inspects its ZIP contents. It does not run an install step or overwrite the workspace `dist`. Temporary test bundles, workspace copies, and VSIX files are removed in `finally` cleanup paths.

The tests exercise real production code rather than copied test implementations. `origin.test.ts` imports the production `normalizeTrustedBrowserOrigin()` function. `trusted-origins-panel.test.ts` instantiates the production `BridgePanelProvider`, executes the inline JavaScript from the actual rendered Webview HTML in `node:vm`, drives real `input`, `click`, and `message` handlers, and separately exercises the production Host save handler. `session-management.test.ts` drives the real session status snapshot, Webview classification, host-side idle-session cleanup, stale-UI request/SSE race protection, and immediate refreshed status response. `bridge-start-command.test.ts` activates the real extension command registration and verifies that `BridgeStartCancelledError` returns the current status while an ordinary `Error` still rejects. `tunnel-lifecycle.test.ts` instantiates the production `BridgeManager`, drives its real start/stop/recovery paths for Cloudflare Quick, Cloudflare Named, and ngrok, and enters automatic recovery by emitting the fake tunnel process `exit` event.

Only runtime boundaries are replaced in the test build: a minimal VS Code API fake, controllable child processes, a fake local HTTP server, and controlled public-health `fetch` responses. Those substitutes make race ordering deterministic without real installers, external network calls, or long sleeps. They do not replace the trusted-origin normalization, Webview state machine, Host save logic, Bridge lifecycle generation/cancellation guards, or recovery loop under test.

The Windows package validation is intentionally Windows-only because this release workflow only guarantees full Windows acceptance. On another platform a complete `npm test` fails with a non-zero exit code and reports that the Windows release-package validation is unsupported; `npm test -- --skip-package` is the explicit opt-in for running only the core regression tests there. The package test derives the VSIX entry prefix from the actual ZIP, requires the production manifest, freshly built bundle, icon, runtime ripgrep binary, localization files, READMEs, and changelog, and rejects `tests/**`, test-build artifacts, mutation artifacts, and temporary test configuration.

These tests are regression coverage, not an installation or end-to-end service environment. Fake VS Code/process/network behavior does not replace testing installation in a real VS Code Extension Host, cross-platform installation, or live Cloudflare/ngrok connectivity.

For one-off mutation acceptance, `node tests/run-tests.mjs --match origin --skip-package`, `--match trusted-origins-panel`, or `--match tunnel-lifecycle` can run an isolated subset. Mutation checks are not part of daily `npm test`; perform them only in a copied temporary repository and delete the copy afterward.
