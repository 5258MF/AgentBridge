# Change Log

## 0.1.13 (2026-09-17)

- **Continuous Cloudflare public-health visibility** — Cloudflare Quick and Named Tunnel now verify the public MCP endpoint every 10 seconds after startup, distinguish healthy, transiently unstable, and unavailable states, and expose the result consistently in the Configuration and Session views. ngrok retains startup verification and an explicit manual check without background polling that would consume request quota.
- **Bounded and generation-safe health checks** — each background check has an eight-second wall-clock budget, a single-flight guard, abortable fetch/JSON/DoH/direct-HTTPS stages, strict non-redirecting HTTP semantics, public-IPv4 filtering, and tunnel-generation ownership so Stop/Start cannot inherit stale results, timers, DNS cache entries, or pending requests.
- **More resilient tunnel recovery** — unexpected tunnel process error, exit, or close keeps the local MCP server alive and reconnects with bounded 1/2/4/8/15-second backoff. HTTP listener ownership, late MCP initialization, Quick Tunnel URL updates, local smoke startup, child termination, and failed-listener cleanup are now protected against stale lifecycle callbacks and overlapping teardown.
- **Clearer health presentation** — the compact public-health badge sits beside AgentBridge in the Session footer and remains visible from the collapsed Connection Settings summary. Warning state contrast now uses high-contrast badge text with a yellow indicator and outline, while the established healthy and unavailable styling remains unchanged.
- **Expanded deterministic regression coverage** — production-path tests cover continuous monitoring, manual checks, hard deadlines, redirects, response/request failures, DoH boundaries, stale generations, Stop/Start recovery, pre-listen shutdown, late sessions, Windows taskkill fallback, Webview completion IDs, and isolated VSIX packaging.

## 0.1.12 (2026-09-16)

- **Cloudflared startup diagnostics and faster failure guidance** — Cloudflare Quick and Named Tunnel startup now consumes per-process connectivity prechecks and transport lifecycle logs, distinguishes DNS and dual UDP/TCP 7844 failures, and stops waiting for the full public-health timeout when cloudflared has already reported a hard connectivity failure. Repeated public-health failures are throttled, route tokens remain redacted, and the resulting guidance is localized.
- **Safer QUIC-to-HTTP/2 recovery** — an auto-selected QUIC connector that fails before registration receives one bounded HTTP/2 replacement attempt. Replacement waits for the old child to close, records the protocol requested for each exact process, honors explicit protocol changes made during startup, and never mistakes an explicit HTTP/2 failure for QUIC instability or enters a recursive fallback loop.
- **Tunnel lifecycle races closed** — health checks are aborted when their child exits, stale health success and old-child callbacks cannot overwrite a newer tunnel, Stop waits for real child closure under the existing bound, and a Start requested while Stop is still releasing resources now waits and performs a genuine restart instead of returning a stale running snapshot.
- **Session activity cleanup** — the Session view adds a compact **Clear history** action that removes finished tool-call and progress history while preserving running tools, Todo state, MCP sessions, and cumulative statistics. Session headings stay on one line with ellipsis under narrow widths, and cleanup immediately returns refreshed status.
- **Client-neutral temporary-address guidance** — the copied temporary MCP address notice now asks users to update the address in their MCP client instead of naming a specific web client.
- **Expanded lifecycle regression coverage** — deterministic tests now cover Cloudflare Quick, Cloudflare Named, and ngrok startup/recovery; exit/close ordering; stale health responses; Stop/Start concurrency; protocol changes during fallback; explicit HTTP/2 failures without protocol logs; and isolated production VSIX packaging.

## Unreleased


### Search and file tools

- **The Node walk applies the global git exclude, as ripgrep does** — a global ignore file (the one `core.excludesFile` names, or `~/.config/git/ignore` by default) is applied by ripgrep in every directory, inside a repository or not, and the walking engine read none of it: a machine that has one answered differently from the same tree on a machine that does not. The file is now read from the same places git would read it, `core.excludesFile` from the per-user config with a `~` expanded, and applied to every path in the walk. Include directives and the system config are not followed, which is the one thing this does not do that git does.
- **An ignore rule from a directory above the workspace is anchored where git anchors it** — the paths the walk hands a rule are written against the workspace root, but the distance collected for a rule found above the walk was measured against the walk root, so a scope that was a subdirectory of the workspace had its own directory put in front of every candidate twice. A pattern carrying a slash (`pkg/secret.txt`, the ordinary way to name one file) then matched nothing at all, and the fallback listed a file ripgrep and git hide. Bare filenames are matched on their last segment, so they kept working, which is why the existing tests did not see it.
- **The Node walk reads the ignore files above the scope root, too** — ripgrep reads the ignore files of every directory on the way up, so searching `pkg/` in a tree whose root hides `pkg/.env` answers the same as searching that root. The walk started with no rules at all and read only the directories it walked past, so a scope below the file holding the rules listed what ripgrep had hidden — the same disagreement as a nested file, one level the other way. Those files are now collected before the walk starts, ordered outermost first so the nearest directory still wins, and a pattern from above is matched against the walk's own path with the distance prefixed on, which is how that directory names it. Whether a directory is above the workspace is decided by reading `..` as the parent and `../` as the way out rather than by a prefix test, which read a directory named `..cache` as being above the workspace and then anchored its rules where they matched nothing.
- **An exclude that does not care about case no longer rewrites the pattern** — case-insensitive matching was done by lowering both the path and the pattern to one case, and a pattern is not text: `[A-z]` is a range that reaches `[`, `\\`, `]`, `^` and `_`, and lowering it turned it into `[a-z]`, which reaches none of them. ripgrep, given the same exclude as `--iglob`, answers `[` for `[A-z]` and `a` for `[A-Z]`, so the two engines were hiding different files. The pattern is compiled instead of rewritten, and the result was checked against `rg --iglob` on twenty-one path and pattern pairs, including braces and negated classes.
- **Both engines read the same ignore files, in a git repository or not** — ripgrep reads `.gitignore`, `.ignore` and `.rgignore`, and honours `.gitignore` only when the directory is inside a git repository. The Node walk read `.gitignore` alone, and read it everywhere, so a tree ruled by a `.ignore` listed files here that ripgrep hid, and a folder that is not a repository had the opposite disagreement about `.gitignore` itself. The walk now reads all three names, ordered so `.rgignore` outranks `.ignore`, which outranks `.gitignore` — the precedence ripgrep uses — and ripgrep is passed `--no-require-git` so both engines answer the same question in either kind of directory. An ignore line is read the way git reads it as well: a leading space is part of the name it names, so ` build` no longer hides `build`; a `#` opens a comment only at the very start of a line, so ` #foo` is a pattern rather than a line that was dropped; and spaces at the end go unless the line escaped them, so `foo  ` is `foo` while `foo\ ` still names a file whose name ends in one. Checked against `git check-ignore` rather than read off the documentation. An escape inside a pattern now stands for the character it escapes and nothing else: `\/deep` was unescaped into a leading `/`, stripped as an anchor, and matched at any depth, while git reads it as a name no path here begins with.
- **A search scoped to one file reports where the match really is** — ripgrep emits paths relative to the directory it ran in, and a file scope makes the child run one level up, because a file cannot be a working directory. The reader resolved those paths against the scope itself, so `path: "pkg/.env"` turned ripgrep's `.env` into `pkg/.env/.env`: the match was still counted and the surrounding lines were read from the right file, but every one of them was labelled with a path that does not exist. The directory the child runs in is now worked out once and used both as its `cwd` and as the base for what it reports.
- **A file that vanishes mid-search no longer fails the whole search** — the walk lists its candidates and then reads them, and a file can disappear in between: a build cleaning up, an editor writing over it. That surfaced as `FILE_NOT_FOUND` with "Search path does not exist", which is a different failure altogether, and it abandoned the rest of the tree rather than continuing without the one file. The fallback now skips it, the way `find_files` already did, so the two agree. A vanished file is still one entry the tree lost, not the search path: the one exception is a `path` that names a single file, which is the whole search — that one is reported as `FILE_NOT_FOUND`, because answering "no matches" for a file that no longer exists says it is there and does not contain the text.
- **A find or search that found something still says what it skipped** — the note naming the active filters only appeared when the result was empty, so the answer a caller is most likely to trust — a non-empty one — said nothing about the files that had been filtered out of it. Both tools now name the filters in force on every result, and the wording distinguishes the two cases: an empty result is told it is not proof of absence, a non-empty one that anything inside the excluded set is missing from it. The tool descriptions say the same, because a model reading them has no way to know that a result can be partial by default. The `filters` field already carried the two flags; the note no longer waits for a zero.
- **A file named as the search scope is actually searched** — `search_files` with `path` pointing at one file never reached ripgrep: the child was spawned with that file as its working directory, which cannot be a file, so it failed with `ENOENT` and every ripgrep candidate was discarded as unusable. The search then fell back to the Node engine, which applied the walk's filters to a file the caller had named — a hidden file such as `.env` came back as no matches, and so did any file past the fallback's 2 MB ceiling, neither of which is true of ripgrep. The child now runs one directory up with the file's own name as its search root, and a file the caller named is no longer filtered for being hidden or large. Searching a directory is unchanged: hidden paths are still skipped there unless `include_hidden` is set.
- **`search_files` refuses an ill-formed glob the way `find_files` does** — `include` and `exclude` are checked for unclosed character classes, unbalanced alternate groups and trailing escapes, and answered with an error. They used to be handed straight to ripgrep, which only settles them when a ripgrep is installed: the Node fallback reads the same pattern as a literal, so `src/[` was an error under one engine and a quietly different search under the other.
- **`find_files` and `search_files` honour a `.gitignore` anywhere in the tree** — the Node fallback read only the `.gitignore` at the scope root, while ripgrep reads the one in every directory it walks past. On a tree holding `sub/.gitignore` with `nested/` in it, ripgrep skipped `sub/nested/` and the fallback walked straight into it, so one call listed different files depending on whether a ripgrep happened to be installed. The rules now travel with the walk: each directory contributes the patterns in its own `.gitignore`, applied to paths relative to the directory that owns them, so `nested/` inside `sub/` means `sub/nested` rather than any `nested` anywhere else. A deeper file still overrules a shallower one, so `sub/.gitignore` can re-include what the root excluded, and `no_ignore` lifts all of them. This entry is about *where* ignore files are read, not *which* names are: both engines read `.gitignore`, `.ignore` and `.rgignore` now — see the entry above.
- **An empty find or search says what it skipped** — a call that matches nothing now names the filters that were in force and the option that lifts each, so `(no matching files)` no longer reads as "this file does not exist". Ignored files and common generated directories are skipped unless `no_ignore` is set, and hidden paths unless `include_hidden` is. A caller that could not see a gitignored file had no way to tell that apart from the file being absent, and went on to create it from scratch. How many paths the filters removed is deliberately not reported — ripgrep does not say what it declined to walk — but whether a filter was applied at all is enough to know a second call is worth making. Both results also carry the active filters as a `filters` field.
- **`list_directory` hides a differently-spelled generated directory** — the shared exclude names are compared in lower case, so an entry called `Vendor`, `Build` or `Dist` is hidden the way `vendor`, `build` and `dist` already were, which is what `find_files` and `search_files` do. An exact comparison let them through, so on a case-insensitive filesystem a listing showed or hid a directory depending only on which spelling it was created with. `no_ignore: true` still brings any of them back.
- **`find_files` and `search_files` hide the same generated directories** — the built-in and configured excludes are matched case-insensitively by both tools and both engines, so a directory named `Vendor/`, `Build/` or `Node_modules/` is hidden the way `vendor/`, `build/` and `node_modules/` are. They reach ripgrep as `--iglob`, which is case-insensitive per glob, instead of as `--glob` riding on the whole-command `--glob-case-insensitive` switch: `find_files` sets that switch and `search_files` never does, because `search_files`' `case_sensitive` governs the text being searched rather than the paths. So the same directory was hidden by one tool and listed by the other, and by `find_files` hidden or listed depending on whether a ripgrep was installed and on which `case_sensitive` the caller passed. The caller's own `patterns`, `include` and `exclude` still follow `case_sensitive` exactly as before; only the noise-reduction built-ins stopped following it, which is what makes `case_sensitive: true` no longer bring a `Vendor/` directory back.
- **A cancelled listing or search is answered as a cancellation** — `find_files` and `search_files` report `ABORTED` when the caller's signal is aborted while ripgrep is running. Cancelling kills the child, which then closes with no exit code and the signal that ended it; that could be read as a failed ripgrep and returned as `IO_ERROR` ("ripgrep exited with code null") rather than as the cancellation it was. Which of the two reached the promise first decided the answer, and the exit handler no longer depends on it. A ripgrep killed by a signal the caller did not send is still reported as an error.
- **`find_files` and `search_files` try another ripgrep before giving up** — a ripgrep that refuses the flags it was handed, typically an older or stripped-down build, is now treated as unusable and the next candidate is tried: `RIPGREP_PATH`, then the bundled binary, then a bare `rg`, and finally the built-in Node engine. Such a build previously failed every listing and every search on that machine. A fatal exit for any other reason — an unreadable path, or a glob the caller or `agentbridge.files.excludeGlobs` supplied — is still reported instead of being quietly retried away, because an engine that does not read globs the same way would answer with exactly the file a rejected exclude was meant to hide.
- **Larger files can be read without a line range** — the implicit-read ceiling for `read_files` rose from 2 MB to 8 MB and is now the `agentbridge.files.veryLargeFileBytes` setting (262144-134217728). Generated bundles, lockfiles and large configuration files routinely pass 2 MB, and the bytes actually returned stay capped independently of this threshold. Reading a range that starts past the last line is now an `INVALID_LINE_RANGE` error instead of an empty result that looks like an empty file — including on an empty file, where `start_line: 2` used to come back as success with the 2 echoed back. `start_line: 1` on an empty file still reads, because that is how a caller asks for one.
- **File excludes are configurable and shared by all three tools** — `find_files`, `search_files` and `list_directory` work from one built-in glob list, and `agentbridge.files.excludeGlobs` adds to it. Previously `list_directory` kept a shorter list of its own, so directories the others hid still appeared there. An include glob no longer outranks the excludes it is meant to narrow in `search_files`, matching how `find_files` has always ordered them; the Node fallback also stopped pruning directories by file globs, which made a search with an include find nothing at all when ripgrep was unavailable. Both search engines now resolve include and exclude globs against the same base as well: ripgrep matches them relative to the search root it was handed, and the Node fallback passes that same root-relative path instead of a workspace-relative one, so an include or exclude means the same thing whichever engine answers.
- **Search columns count characters** — `search_files` reports a match column as a character position rather than a byte offset, so a line containing CJK text no longer reports a column past the end of the match, and both engines agree.
- **A progress percentage past the end is reported as the end** — `report_progress` was the one bounded number left that refused a value outside its range, so a caller reporting 120% had the whole report turned away, message included, and the panel it exists to feed heard nothing. It now goes through the same helper as the rest: brought into 0..100, with the answer naming what was used. A percentage past the end is a caller being optimistic, not a call that cannot be answered.
- **The image ceiling is checked against the bytes that were read** — `read_image_file` asked the size of the file and never the size of what came back, so a file that grew between the two was decoded whole and handed over as base64, which is the thing the ceiling exists to prevent. The bytes are now counted after the read as well, and the ceiling itself is the new `agentbridge.files.imageMaxBytes` setting (262144-134217728, 5 MB by default) instead of a number in the source: an image is base64 in a conversation, so how large one may be is a decision about the project and not about the tool.
- **`read_image_file` answers a failed call as a failure** — it returned its errors as a successful result with `ERROR <code>: <message>` inside the text, so a caller that trusts the result's error flag read a refusal as an image it had been given. There is one file in the call and nothing else in it succeeded, so the result now carries `isError` and the panel shows the entry as an error. `read_files` is unchanged: it reports one unreadable file as a row of an answer that otherwise succeeded.
- **`search_files` drops a match reported at a path outside the scope** — the path ripgrep prints is text from a child process and was resolved without question, so a report naming `../escape.txt`, or an absolute path elsewhere on the machine, was turned into a match: its lines were read from a file outside the scope and shown as a result of searching inside it. Nothing in an ordinary run produces such a path, which is the argument for not trusting one rather than for assuming it cannot arrive — a replaced binary, or a symlink that moves a directory mid-search, reaches this reader the same way. Out-of-scope matches are now dropped and counted in `skipped_outside_scope`, with a note saying how many were dropped and why. A file scope is that one file and nothing beside it.
- **A file named as the search scope is no longer filtered at all** — `path` pointing at one file still had the walk's filters applied to it: hidden, the built-in generated directories, `agentbridge.files.excludeGlobs` and the caller's own `include` and `exclude` could each turn a file the caller pointed at into "no matches", which reads as the file not being there. ripgrep applies none of them to a path it was handed on its command line — checked against the bundled binary, `--iglob '!**/node_modules/**'` and an include naming another suffix both leave `node_modules/pkg/secret.txt` in the answer — so the same call came back with the match under one engine and empty under the other. A named file now skips all of them in the fallback too. `excludeGlobs` is guidance of the same kind as the rest rather than a boundary this lets a caller through: `read_files` has never consulted it. Walking a directory is unchanged.
- **The ignore parser agrees with git on escapes and on directory patterns** — two places where it did not. A line beginning with `#` was dropped as a comment even when the `#` was escaped, so `\#report.txt` - git's way of naming a file whose name starts with `#` - was no rule at all; the escape is kept in the pattern now and undone after the leading `!` has been read, so `\!keep.txt` is a file called `!keep.txt` and not a re-include of `keep.txt`. And a pattern ending in `/` matched a file of the same name: `docs/` hid a file called `docs`, where git hides only the directory. Such a pattern is now tried against each directory the path passes through, and against the path itself only when it is a directory. Checked against the bundled ripgrep on a tree with both, and the two engines now answer the same.
- **The Node walk skips a directory an exclude names whole** — `find_files` tested every entry against `**/node_modules/**`, a pattern no directory called `node_modules` matches: only what is under it does. Such a directory was therefore read in full and then discarded one entry at a time, so a workspace with dependencies installed paid for a listing of the whole dependency tree before the first real candidate was considered. A glob of the shape `**/name/**` now prunes the directory by name, which cannot change which files come back - that glob rejects everything underneath it anyway - and globs of any other shape are left alone: `build/` and `**/build` name the directory alone rather than what is under it, `packages/*/gen/**` depends on a parent a bare name knows nothing about, and pruning by name would hide files those let through. The caller's own `exclude` prunes the same way, folded to the case the call asked for.
- **The Node walk of `find_files` stops at a scan budget** — `search_files` has bounded its fallback at 20,000 files for a while; `find_files` had no bound at all, so a call answered by this engine read the whole scope however large it was, which is the entire workspace on a machine where ripgrep is missing or where a per-file permission check forced the fallback. It now stops after 20,000 entries - directories count, because a listing is what costs here - returns what it had already found, and reports `MAX_FILES_SCANNED` in `truncation_reasons` rather than answering as if the tree had been read to the end.


- **An anchored ignore pattern stays in the directory that wrote it** — a pattern with a leading slash (`/deep`) or a separator inside it (`a/b`) names something next to the ignore file and nothing deeper, but the leading slash was taken off the name and then forgotten, so the pattern went on to match at every depth as if it had been written `deep`. `git check-ignore` answers no for `a/deep` with `/deep` in the file and yes for it with `deep` there, and it answers yes for `deep/f.txt`, so an anchored pattern now hides what is under the directory it names as well. Matching it is done against the path alone: the basename, which the shared matcher also offers, is exactly what "at any depth" means, and it is exactly what an anchored pattern is not.

- **`search_files` skips a generated directory the way `find_files` does** — its fallback walk read `node_modules` in full for the same reason the other one did: an exclude of the shape `**/node_modules/**` does not match the directory itself, only what sits under it, so the directory was listed and then discarded one entry at a time. Both walks now prune such a directory by name, and a configured exclude prunes the same way even when `no_ignore` is set, because it names what the agent may be shown at all. The caller's own `exclude` prunes too, folded to the case the call asked for rather than to one case, since that is how the call's own globs are read.

- **A caller's exclude stops the search walk at a directory** — `search_files` answered for directories before it read `exclude` at all, so a bare `assets` or `dist`, which names the directory and nothing under it, hid nothing: the walk went in and then matched the exclude against each file it found, and no file inside is called `assets`. ripgrep reads the glob against the directory too and stops there, so the same call answered two ways depending on which engine ran - `rg -n needle --glob '!assets'` does not report `assets/x.txt`, and `--glob '!**/*.ts'` does not report `x.ts/inside.txt`, and now neither engine does. `find_files` already read its excludes this way.

- **A glob matched without regard to case now means what the host says it means** — a case-insensitive match compiles the pattern instead of handing it to `path.matchesGlob`, which has no such form, and the compiler disagreed with the host three ways. A `]` written first in a character class was dropped rather than kept, so `[]a]` named `a` and not the `]` it was written for. A `**` that does not own a path segment of its own — `a**b`, `**b`, `a**`, `***` — was compiled as "any characters, `/` included", where the host reads it as the two single stars it looks like and answers `ab` and `axb` for `a**b` but not `a/b`. And a `**` at the end made the directory it stands behind optional, so `a/**` reached `a` itself, which the host does not match. An exclude that one engine reads and the other does not is a file the caller asked never to be shown. `^` is left as it is on purpose: a glob negates with `!`, but the host reads `[^ab]` as `[!ab]` and ripgrep asked with `--iglob` reads it the same way, so making `^` an ordinary member here would be the disagreement. One test now puts thirty-nine globs against twenty-four paths on both sides, so any drift from the host is a failure rather than a difference nobody wrote down.
- **The ignore files a walk climbs through are read once, and the climb stops at the workspace root** — every `find_files` and `search_files` call walked from the scope up to the filesystem root, reading each directory on the way, so a scope three levels down paid for the same files on every call and every call in a search paid for all of them again. The files are read once now, keyed by directory, and a change to one is picked up when the window is reloaded - the way the rest of the configuration behaves. The climb also stops at the workspace root: a directory above it belongs to the machine rather than to the tree the caller opened, and a repository holding several folders, or a home directory two levels up, would otherwise reach into a scope that never named it. Rules from the workspace root down still apply, outermost first.
- **A workspace-relative path is resolved against the folder that holds it** — the file tools were handed every workspace root, but `list_directory`, `run_command`, `lsp` and a click in the panel asked only the first folder, so in a window with two folders a path belonging to the second was reported as outside the workspace, or opened a file that does not exist there. The folder that has the entry is the one a path is resolved against now, and the first folder stays the answer when none does - which is what "." has always meant. `find_files` had the same edge one level down: a scope that is a file in one folder and a directory in the next is the directory.
- **A character class inside a brace is read as a class** — `{[a,b]}` was cut at the comma into `[a` and `b]`, which match nothing, while ripgrep - the engine a default `find_files` hands the same pattern to - reads it as a, b or the comma. The two engines therefore hid different files. An escaped comma and an escaped star are the characters they escape as well.
- **A search without ripgrep stops walking at its budget, whatever the tree is made of** — the fallback counted files only, so a scope of empty directories cost nothing against it and the walk had no ceiling but the cancel button. It counts every entry it looks at now, the way `find_files` does. **The ignore files of a directory are read once whether the walk climbs past it or descends into it**, which is what the cache always said it did. **One file that cannot be read no longer fails a whole `find_files`** - the walk has always skipped a directory it cannot open.
- **A match with no surrounding lines says why** — a file the caller named is the whole search, so it is read however large it is, and then it is too large to keep for the lines around the match. That used to be silent: the match came back with no before/after and no reason, so a file too large for its context looked like one with nothing around it. It is reported now.

### apply_patch and the diffs it writes

- **A blank line in a hunk counts as the context line it is** — an empty line inside a hunk is an empty context line, and the parser pushed it to both sides but left the marker that says which side the previous line belonged to where it was. A `\ No newline at end of file` following such a line was then read against the line before it instead: after an addition it marked the new side only, so the check that the old file really ends without a newline was skipped and the patch was applied to a file it contradicts. The marker now moves with the line, so a blank line is context for this purpose as it already was for every other.
- **`apply_patch` strips both halves of a code fence alike** — a fence that was opened and never closed was forgiven, while one that was closed and never opened was refused as content after the closing directive: the same wrapper, the same slip, and two answers depending on which half the caller dropped. Both ends are removed now. Nothing else about a patch is relaxed - prose after the closing directive is still refused, fenced or not.
- **`apply_patch` reads a patch that arrives in a code fence, or after a blank line** — the patch text had to begin with `*** Begin Patch` on its very first character, so a caller that wrapped it in a fence or left a blank line in front was refused with a message about the opening directive. Neither wrapper changes what the patch says, and a round trip to remove it teaches the caller nothing about the patch. The outermost fence and the blank lines around it are stripped now; content after the closing directive is still refused, fence or not, and text that is not a patch still fails on the opening directive.
- **`apply_patch` folds path case only where the filesystem does** — the duplicate check and the expected-version lookup compared paths lower-cased, which is right on Windows but wrong on Linux, where `A.txt` and `a.txt` are two files: a patch editing both was refused as touching one path twice, and a version keyed for one was offered as the version of the other. Both now fold case on Windows and macOS and leave it alone elsewhere.
- **Add File onto an existing empty file names the way in** — `*** Add File:` still refuses a path that is already there, but when the file it lands on has no content the error now says how to write to it: a file with no lines has exactly one position, so `*** Update File:` with a hunk of additions only (no context, no removals) is unambiguous there. It still needs the `sha256:` version `read_files` reported, like any other edit. Previously the error only named the conflict, which left deleting the file first as the only visible way forward.
- **One-line hunk ranges carry no count** — the generated unified diff writes `@@ -1 +1 @@` rather than `@@ -1,1 +1,1 @@`, which is the shape git writes, so a diff produced here can be handed back to `apply_patch` or read by any git-aware tool without meeting a header it does not recognise. A zero-line range keeps its `,0` either way, so a pure insertion still says where it landed.
- **`apply_patch` requires an expected version for edits and deletes** — every `*** Update File:` and `*** Delete File:` target must carry the `sha256:...` version `read_files` returned for it. A mismatch still returns `STALE_FILE`, and a missing entry now returns `MISSING_EXPECTED_VERSION` instead of editing or deleting a file the agent never read. Files the patch only adds need no version.
- **Canonical diffs mark files that end without a newline** — the generated unified diff now emits `\ No newline at end of file`, so `a\nb` and `a\nb\n` no longer render as the same change. `apply_patch` accepts the marker in incoming patches as well, so a diff handed back to a model can be reused without being rejected.
- **Canonical diffs are written in git's shape** — inside one changed run every removal is listed before every addition, so a replacement reads as `-old` then `+new` however the two sides interleaved, and `\ No newline at end of file` is emitted directly after the line it describes, so the marker belonging to the old side no longer ends up beside the new side's line. `apply_patch` reads it the same way: following a removal it says the old file ended without a newline, following an addition the new one, and following an unchanged line both. A marker that lands anywhere else in the hunk is still rejected as `INVALID_PATCH`, because there it would describe a line that by definition continues.
- **A patched file's trailing newline follows the hunk that reaches its end** — `apply_patch` used to let the last hunk of a file decide whether the file ends with a newline, so an edit in the middle silently added one to a file that had none. The canonical diff reports a trailing-newline change even when the rest of the file changed too, so the diff handed back to a model does not understate what happened.
- **Paths are resolved once per `apply_patch` call** — the lock pass, the preflight pass and the write share one `realpath` result for each path, including the paths a patch creates. A symlink swapped between them could previously leave the lock held on one file while another was checked and written.
- **`apply_patch` says what a rename looks like** — its description named "Add/Update/Delete/Move directives", but there is no Move directive: a rename is an `*** Update File:` section carrying `*** Move to:` on the next line, and a model that invented `*** Move File:` was refused. The four sections are named as they are written, with the rename spelled out.
- **A code fence closed twice is still a wrapper** — `apply_patch` forgave a fence that was opened and never closed, and forgave one that was closed without being opened, but answered a second closing fence as prose after `*** End Patch`, so a patch the caller had merely fenced twice was refused. Every closing fence is wrapper now, whichever half the caller got wrong. Content that is not a fence is still content wherever it sits, so prose after the patch remains an error.

### Diagnostics and language features

- **A long diagnostic message is cut between characters** — the report shortens one message at 2,000 characters, and both the cut and the count behind it counted UTF-16 units, so a character written outside the first plane - an emoji, a rarer CJK extension, a mathematical symbol - counted as two and could be cut in half: the message ended in an unpaired surrogate, which is not text a caller can print or compare, and which a JSON writer answers with a replacement character or with an error. Both count characters the way a reader counts them now, so the character at the cut stays whole and the number that follows the message says how many were really left out.

- **`get_diagnostics` says what the editor was looking at, so an empty answer is unambiguous** — "no diagnostics" is what a clean directory looks like and also what a directory nobody has opened looks like, because diagnostics exist only for documents a provider has published them for. The report now carries `documents_with_diagnostics` and `open_documents` for the scope, and a note next to an empty result spells out that it is not proof the files are clean and says whether anything in the scope is open at all.
- **`get_diagnostics` reports a severity value it cannot use instead of failing on it** — a name that is not one of error, warning, information or hint was refused outright, and one wrong name among good ones was dropped without a word, so a caller looking at a filtered answer had no way to know it was filtered. The report now names the values it ignored and says whether a filter was applied at all: a list with nothing usable in it is no filter, and the report says so rather than answering "no diagnostics" about a directory that has some.
- **A text that has to be shortened can no longer come back longer** — `boundedText` pasted the head of the string and then a slice of its tail, and the tail slice was written as `slice(-(budget - head))`. When the budget is no larger than the truncation marker itself that is `slice(-0)`, which is `slice(0)`: the whole string, appended after the marker, from a helper whose only job is to shorten. Nothing reaches that branch today - the one caller caps hover text at 16000 characters - so no report is behind this, and the guard is what makes the helper right for a cap that small instead of being right by accident of arithmetic.
- **`lsp document_symbols` reports the symbols inside a class, not just the class** — a DocumentSymbol carries its children, and that is where a class keeps its methods and fields. Only the top level was walked, so a TypeScript or Python file came back as a handful of classes with nothing in them. The tree is flattened now, depth first, and each result names what encloses it, so a method reads as `App.Router.match` rather than a bare `match`. Providers returning the older flat shape are unchanged.
- **`list_directory` says how much a short listing saw** — a truncated answer reported `truncated: true` and nothing else, so a caller could not tell a directory holding one more entry from one holding four hundred, and had no basis for deciding whether to ask again or narrow the scope. The walk now counts what it looked at as well as what it kept, reported as `entries_seen`: the directory it stopped in is finished, so the count is a number rather than a guess, and a note says that a directory below it was not descended into once the answer was full. `max_entries` still bounds what is returned, not what is counted.
- **`list_directory` names an entry that is two things at once** — `FileType` is a set of bits, and a link is reported as SymbolicLink combined with whatever it points at: a symlink to a file is 65, to a directory 66. The listing compared the whole number against one member at a time, so neither matched and both were reported as unknown, an entry the tool declined to describe. The link bit is what a listing is asked about and is now answered first. A link to a directory is still a link and is still not descended into, which is what keeps a link that points at an ancestor from being walked as a cycle.
- **`get_diagnostics` compares a Windows scope the way Windows compares paths** — the scope was matched against each reported path as a string, while the check that the path lies inside the workspace folded case. On Windows `SRC` and `src` name one directory, so a scope spelled with different case than the one the language server reported answered "no diagnostics" for a directory that has some. Both now use the same comparison.

- **A shortened diagnostics report keeps the errors, not the first files it met** — the report was cut during the walk, as soon as it held `max_results` rows, and only afterwards sorted by severity. With a noisy file reported first, a hundred hints filled the answer and the one error in a file reported later was dropped — while `total_matching` still counted it and `truncated` still said the report was short, and the tool description still promised that errors come first. On a repository with lint noise, a caller asking for ten diagnostics got ten hints and no way to know a compile error existed. Everything matching is now collected and shortened after the sort; the rows are small objects and the diagnostics were already in memory.

- **One diagnostic cannot spend the whole report by itself** — a type error that expands its type can run to tens of thousands of characters, and nothing bounded it: one entry could take the entire budget of the answer it was sharing with every other file in scope. A message is now shortened at 2000 characters with a marker saying how much was left out, and is folded onto one line, because the report is a run of lines a caller reads positionally and a diagnostic carrying its own line breaks reads as several entries.

- **The open-document note counts documents instead of writing `document(s)`** — an empty report says how many documents in the scope are open, and wrote it as `1 document(s)`, which reads as a placeholder a caller has to parse rather than as English. One document is now singular and several are plural; nothing else about the note changed.

### The managed terminal

- **A temp script that cannot be deleted no longer keeps its directory** — the script is written into a directory `mkdtemp` made for the run and both are taken away afterwards, but when the deletion still failed after its one retry the code reported the failure and returned without touching the directory, so a file nobody could delete kept a directory nobody needed until the machine was restarted. The directory is removed either way now: it usually fails as well while the file is held, and succeeds when the lock is released a moment later, which is the reason the retry exists. The warning is still reported, and a directory this code did not make is still left alone.

- **A shell that never reports ready keeps its terminal instead of losing it** — the first-prompt wait ends in the same failure whether the shell timed out or died before its prompt, and that path disposed the terminal and dropped its slot. The result was an empty pane *and* "no longer available" from the activity log at the same time, with nothing left to look at — and whatever the shell printed is the only evidence there is about why it never got there. The terminal is now left open with its shell still running, the slot is kept so it can still be opened and marked so that it is never handed out again (the next command starts a fresh terminal), and the error names the terminal and says how to run without the prompt protocol. The pool reclaims a broken terminal before a working one when it needs the room.
- **PTY commands no longer wait out the first-prompt timeout on a host whose node-pty reports pid 0** — the marker a managed shell writes on every prompt carries the shell's own pid, and a marker whose pid is not the pid the PTY spawned is refused so that a nested or remote shell cannot end the outer command early. The check treated every finite number as a real pid, and the node-pty build VS Code ships reports **0** for a ConPTY session on Windows: nothing can match 0, so every marker was dropped, the shell never reported ready, and each `run_command` in the default PTY mode failed with "did not reach its first prompt within 8 seconds" while the managed terminal stayed empty and was then disposed. A pid of 0 identifies no process, so it now takes the same route as a missing pid — accepted, which is the failure mode this guard was already documented to prefer. Measured against the same node-pty outside the extension: the shell starts, prints, and emits its marker carrying the real pid, so the pty itself was never the problem.
- **A block comment before `param(...)` no longer breaks a bridged PowerShell script** — the encoding prelude is inserted after the parameter block because PowerShell requires `param()` to be the first statement. Comment lines and `#requires` were skipped when looking for that block, but `<# ... #>` was not, so a script opening with a block comment had no recognised parameter block and the prelude was written at the very top, in front of `param`, leaving a script that does not parse. Block comments are now skipped the same way.
- **Exit markers are checked against the shell that owns them** — each prompt marker carries the emitting shell's PID, and a marker from another process (typically `bash` inside `ssh` or `docker exec`, which inherits the per-prompt hook) no longer ends the outer command early and overwrites its working directory with the nested shell's. A marker with no PID is still accepted, because a terminal restored by VS Code from a previous session runs the older hook and refusing those would hang every command in it.
- **Bridged commands and direct runs use the managed shell** — the temp-script bridge and `execution: "direct"` now invoke the shell configured through `managedShell.*` instead of hard-coding Windows PowerShell 5.1 and `/bin/bash`. A PowerShell 7 or zsh override is therefore honoured for multi-line, non-ASCII and over-long commands, instead of those being downgraded to a shell that may not understand their syntax.
- **Bundled PSReadLine for Windows PowerShell 5.1** — managed PowerShell terminals now prepend the extension's `vendor/` directory to `PSModulePath`, so ConsoleHost resolves the bundled PSReadLine 2.3.4 instead of the Windows in-box 2.0.0, whose negative cursor-position handling produces ConPTY rendering artifacts. The payload contains only PSReadLine, so no other module is shadowed, and it is resolved relative to the compiled bundle first and the installed extension layout second; when absent, the shell silently falls back to the in-box version. The module's BSD 2-Clause license and attribution are recorded in `THIRD_PARTY_NOTICES.md` and the payload's own `License.txt`.
- **`run_command` execution modes** — `run_command` accepts an optional `execution` parameter (`pty` default, `direct`). `direct` runs the command through a one-shot child process with piped stdio: the exit code comes straight from the process, so builds, tests and scripts avoid the prompt protocol, do not consume a terminal slot, and never appear in a terminal view. `stdin` is closed, so interactive input is unsupported; `background=true` is rejected in this mode, and `send_command_input` reports a clear error for a direct command. On timeout the child keeps running and stays pollable with `get_command_output`, mirroring PTY semantics. On Windows a negative exit code reported as unsigned 32-bit is normalized back into signed range.
- **Temp-script bridge for fragile commands** — commands containing CR/LF, non-ASCII characters, or more than 1024 characters are no longer typed into the readline layer. They are written to a temporary script and executed as a single ASCII one-liner, avoiding continuation-mode buffering (dropped lines, later commands appended to an unfinished statement), lossy fast ConPTY pastes, and console code-page mangling. On Windows the script carries a UTF-8 BOM and an `[Console]::OutputEncoding` prelude — inserted after a leading `param(...)` block, since PowerShell requires it to be the first statement — plus a native exit-code guard that propagates `$LASTEXITCODE` (or exit 1) when the final statement failed, instead of masking the failure as exit 0. The temp script is unlinked once the command settles.
- **`run_command` result header is field-stable** — the `RUN_COMMAND` block now carries `execution`, `script_bridge`, and `hint` alongside the existing fields, and `COMMAND_OUTPUT` reports `execution`, so callers can distinguish PTY from direct runs and detect bridging by field name rather than line presence.

- **A bridged command is written where only the shell can read it** — the temp script a long, multi-line or non-ASCII command is bridged through sat at a predictable path in the shared temp directory, `agentbridge-run-<command id>.(ps1|sh)` with the id a timestamp and a counter, and it was written without an exclusive flag: anything on the machine that could guess the next id could leave a file or a symlink there and have the next command's text written through it, into a file of its choosing. The PowerShell branch also set no mode, so a command carrying a secret was readable by every other account on the machine. Each script now gets a directory `mkdtemp` creates — unguessable, and created exclusively — and the file inside it is opened with `wx` and mode 0600 (0700 for the POSIX script), so a name that is somehow already taken is an error rather than a write through whatever is sitting on it. The directory is taken away with the script.

- **A direct run hands `cmd` the switch `cmd` understands** — `execution: "direct"` built its arguments as `<shell> -c "<command>"` for every non-PowerShell shell, and `cmd` has no `-c`: it takes `/c`. A cmd-managed host therefore had every direct command rejected by the shell itself, which reports an unknown switch rather than running anything. cmd now gets `/d /s /c`, the shape that neither runs an AutoRun entry nor re-quotes the command; the POSIX shells keep `-c`, and the PowerShell families were never affected because a direct run bridges them through a script.
- **The unsupported-shell error names the shells the setting accepts** — it said PowerShell on Windows, bash on Linux and zsh on macOS, leaving out Git Bash and MSYS zsh, which are Windows shells here and are valid choices for `agentbridge.bridge.managedShell.windows`.

### The Bridge, its endpoint and its tunnels

- **An oversized request body is read to the end, so the client can see the 413** — `readJsonBody` stops buffering once the body passes 8 MiB, and it used to `pause()` the request there. Pausing kept the socket alive, which was the point, but a client cannot read the response until it has finished writing, and a body the server stops reading never lets that write finish: a 9 MiB request against the bridge came back as `SSL: UNEXPECTED_EOF_WHILE_READING` with no status and no explanation. The remainder is now read and discarded, and the buffer already collected is released. What the cap protects is memory, and that is still protected.
- **Every response gets the canonical session header, not just a POST** — the rewrite that spells `mcp-session-id` the way the protocol documents do was applied at the two points inside the POST handler, which are the branches an `initialize` goes through. The SDK writes that header from four places, so a GET stream or a DELETE answer would have left with the lower-case spelling, and the fix would have been invisible until someone noticed a second header going out the wrong way. The response is now wrapped once, at the top of the request handler, before any branch can write to it.
- **A repeated `Mcp-Session-Id` is refused rather than looked up** — Node collects a header that arrives more than once into an array, and the bridge read that array as if it were the string the type said it was. The session key became `"abc,def"`, which can only miss, so a client that sent the header twice was answered with "the session may have expired" and went looking for the wrong problem. The protocol allows exactly one, so a repeated header is now answered as the malformed request it is. No client that sends it once is affected.
- **A window that does not start the Bridge still checks the tunnel** — the tunnel check only ran when `agentbridge.bridge.persistentMode` was on, so a machine whose cloudflared is missing, or whose named-tunnel hostname is unset, looked exactly like a working one until the user started the Bridge and waited for it to fail. Activation now runs the check either way — it starts nothing, it reads the configured provider and asks its CLI for a version — and logs what it found to the output channel. The status bar tooltip for a Bridge that is not running also carries the last tunnel error, so the answer is visible without opening that channel. Persistent mode still starts the Bridge as before, and does not pay for a second check.
- **The endpoint token is half as long** — the token in the MCP endpoint path was 32 hex characters, the shape `randomBytes(16).toString("hex")` produces. It reads as a UUID rather than as an opaque path segment, and it costs twice the characters every time an endpoint is handed to a model. It is now 16 characters drawn from `0-9a-z`: bytes at or above the largest whole multiple of the alphabet size are redrawn, so all 36 characters are equally likely instead of the first few being favoured by a plain modulo, and the result is about 83 bits rather than 128 — still far past guessing distance. A token already held in `SecretStorage` is left alone, because replacing it would silently invalidate every client already configured with the old address; new installs get the short form, and an existing one gets it by rotating the endpoint from the panel.
- **The MCP session header is spelled the way the protocol spells it** — the SDK emits `mcp-session-id` in lower case, which is legal HTTP but not the spelling the documents use, so a client written from the docs and a client written from the wire disagreed about the name. The bridge now rewrites that one header to `Mcp-Session-Id` on the way out, including in the CORS list that has to name it before a browser will expose it. Header names compare case-insensitively, so no client needs to change.
- **ngrok proxy handling** — the ngrok tunnel process no longer inherits HTTP/S proxy variables. ngrok Free rejects an agent that connects through a proxy with `ERR_NGROK_9009`, and inherited `*_PROXY` variables (both cases, plus `ALL_PROXY`) made that failure reachable from machines where no ngrok-level proxy was intended. AgentBridge now strips them before spawning ngrok and logs that it is connecting directly. `ERR_NGROK_9009` also gets dedicated guidance instead of the generic reserved-domain error, pointing at the ngrok config file's `proxy_url`, TUN-mode proxies, and the upgrade path. New `agentbridge.bridge.ngrokUseHttpProxy` setting (default `false`) lets Pay-as-you-go users opt back into the resolved proxy.
- **Configurable tunnel startup timeout** — the public-health startup budget is now the `agentbridge.bridge.startupTimeoutMs` setting (5000-120000, default 20000) instead of a hard-coded 60 seconds. The previous fixed budget made a slow public network fail too early while a failing one kept the user waiting; the default is now lower and adjustable in both directions.
- **Deterministic health failures abort early** — a failed public-health request is classified by walking the wrapped Node error cause chain. DNS failures (`ENOTFOUND`, `EAI_AGAIN`), unreachable or refused/reset connections (`ECONNREFUSED`, `ECONNRESET`, `EPIPE`, `EHOSTUNREACH`, `ENETUNREACH`, `ECONNABORTED`, `EPROTO`), and TLS interception (`certificate`, `self-signed`, `wrong version number`) are deterministic: they cannot succeed by retrying with the same network configuration. An endpoint that answers `401`, `403` or `407` is treated the same way, since a gateway that refuses authentication keeps refusing it. After 3 consecutive such failures startup aborts with an actionable message distinguishing "a proxy is configured and still failing" from "no proxy at all", instead of burning the whole timeout — `404` is deliberately not deterministic, because the health endpoint legitimately does not exist until the tunnel is up. Each attempt is also bounded by the time left in the startup budget rather than by the per-request limit alone, so the DoH fallback and anycast retries cannot run past the window the user configured. Non-deterministic failures reset the counter and keep retrying until the deadline.
- **Oversized MCP requests are answered, not reset** — a body past the 8 MB limit is answered with `413` and a JSON-RPC error explaining the limit. The socket used to be destroyed before the response could be written, so the client saw a connection reset with no explanation.
- **A workspace cannot switch read-only mode off** — the setting is declared application scope, and the comment said as much, but it was read from the merged configuration, which honours the workspace as well: a settings.json committed to a repository could turn apply_patch and run_command back on for anyone who opened it. The user-level value now decides when the mode is on; a workspace may still tighten one project, never loosen it.
- **The proxy bypass list goes with the proxy** — ngrok is spawned with every proxy variable stripped, because the Free plan rejects an agent that connects through one. NO_PROXY was left behind: it is the bypass list for a proxy that is no longer there, and it hands the child an environment that still looks like a proxy was configured. Small in effect, since a bypass list does nothing without a proxy, but it is one variable of the same setting.
- **A failed public-health check says what went wrong** — the request classifies its failure by walking the cause chain: the status it was answered with, a name that does not resolve, a connection that is refused or reset, a certificate that does not check out. The monitor that runs after startup read only whether the check passed and otherwise answered with the text it falls back on when nothing is known, so a panel showing `unstable` did not say why. It names the classified cause now, with the route token redacted as anywhere else.

### The panel and quick open

- **A line and column that are not whole numbers are answered with the first line** — `openResource` asked only whether the value was a number above zero, so 2.5 had its fractional part dropped by the constructor, a negative number landed before the first line and `Infinity` named a line no document has, none of them said anything. Both are now brought into range the way every other number the bridge receives is, so a caller that sent something else opens line 1 instead of a different line entirely.
- **The panel refuses to open anything that is not a web link** — a webview message can carry any string and `openExternal` opens whatever it is given, so a `file:`, `vscode:` or `javascript:` URI reached the operating system as if it were a click on a link. The scheme is now checked where the message is handled and not only where a link is saved, and anything that is not http or https is refused with a message naming what was refused. `HTTPS://` is still the same link.
- **Clearing the tunnel token asks on the page, and a refused language change says why** — both went through `window.confirm` and `window.alert`, which a webview does not implement: `confirm` answers `undefined`, so the dialog silently said no and the clear button appeared to do nothing at all, and `alert` shows nothing, so changing the language with unsaved tunnel or whitelist work simply snapped the select back. Clearing the token now arms a confirm/cancel pair where the button was, and the reason a language change was refused is written into a line under the select, cleared as soon as the work it names is saved.
- **A read image says what it was** — a successful `read_image_file` puts its type and size next to `status` and `path`, the way every other file tool does, and the panel looked for them under a nested `success` that is not there, so an image that was read fine carried no subtitle at all. The presentation now reads the flat shape, and both shapes are asserted together, so they cannot drift apart again without a test failing.
- **A quick open shortcut typed without a scheme is read as https** — the form demanded a full `http(s)://` address and refused `example.com`, which is what people actually type. A value carrying no scheme now gets `https://` in front of it, on both the webview side and the host side, and the field is rewritten so the form shows the address it is about to save. A value that already carries a scheme of its own is handed to the validator untouched, so `ftp://example.com` and a mistyped `htps://example.com` stay errors instead of having a second scheme glued in front of the first. The same reading is applied to `settings.json`: a hand-edited entry without a scheme used to be discarded by the well-formedness filter, and now renders like any other shortcut.
- **The panel and the host agree about what a shortcut address may contain** — the host reads a regular expression whose `\S` refuses every whitespace character, while the form only looked for `charCode <= 32`, so an address holding U+00A0 or another non-ASCII space was accepted by the form and thrown out by the host at save time: one field, two opinions, and the error arriving after the work was done. The form now asks about whitespace the way the host does. A colon in front of the path is also read the same way at both ends — a port when what follows is digits, a scheme of its own when it is not — so `example.com:8080` still gains a scheme while `javascript:alert(1)` is judged as it stands instead of being quietly turned into `https://javascript:alert(1)`, which the validator accepted as an ordinary https address. Hand-edited settings are filtered by that same host validation on load, so a `file:` entry in `settings.json` never reaches the panel.
- **Quick open shortcuts can be edited, and deleting one works** — deleting asked `window.confirm`, which a webview does not implement: it answers `undefined`, so the dialog silently said no and the button appeared to do nothing. A row now confirms in place, swapping itself for a confirm/cancel pair. Every row also gained an **Edit** button, which loads the shortcut into the form above; the form then saves back to the same slot instead of appending, and refuses to take an address another shortcut already holds (its own address is still fine).
- **Buttons that open something say where they go** — hovering any open button shows the address it will open. The label only names the site, and the address is the thing worth checking before clicking. This covers the hero row and the More sites group as well as the shortcuts at the top of the page.
- **Shunova is no longer one of the built-in sites** — the More sites group is Arena, WorkBuddy, Trae, Qwen Work and Manus. `https://arena.ai/agent` is already the Arena button, so nothing needed adding.
- **The todo in progress shows what the agent is doing** — the Session tab's task list reads the newest `report_progress` entry filed against the current todo and renders its phase, message and percent beside it; previously the row read those fields off the todo itself, which carries only an id, a title and a status, so every row drew an empty progress span. The row also picks up the highlight, spinner colour and percent colour its rules were written for — they are spelled `.in-progress` while the row carried the status `in_progress`, so none of them ever applied.
- **The Bridge panel keeps its tab when the language changes** — changing the interface language replaces the whole panel document, which used to drop the reader back on the Config tab and forget the expanded Advanced section whenever a draft was still open. Both now carry across the rebuild.
- **Quick open shortcuts** — a **Quick open** card on the Bridge panel adds user-defined `http(s)` links, which then appear as buttons at the top of the page. Entries are stored in the new `agentbridge.bridge.quickLinks` setting (max 16, name ≤ 40 characters, URL ≤ 500) and are validated on both sides: non-`http(s)` addresses, duplicate addresses and malformed hand-edited `settings.json` entries are rejected or skipped instead of rendering a dead button. Deleting a shortcut asks for confirmation, and the panel follows external Settings edits through the configuration-change listener, so a link added on another machine shows up without reloading.
- **A todo update is on the timeline** — `set_todos` returned before the activity was pushed, so the plan a caller keeps across a whole job left no line in the panel and did not count towards toolCalls. `report_progress` was always recorded, so a job that reported its progress but never restated its plan looked like a job that did nothing between file calls. Both the completed and the rejected case are recorded now.

- **A shortcut address with credentials, or an IPv6 host, is read as https again** — the form and the host both read a colon in front of the path as a port when digits follow it and as a scheme of its own when they do not, which is what keeps `javascript:alert(1)` refused instead of being turned into `https://javascript:alert(1)`. It also stopped reading two addresses that carry no scheme: `user:pass@example.com`, whose colon belongs to the credentials, and `[::1]`, whose colons belong to the address. Both gain the scheme now, told apart from a scheme by the `@` after the colon and by the brackets around the head rather than by a list of known schemes, and `[::1]:8080` keeps working as it did. `javascript:alert(1)`, `ftp://example.com` and a mistyped `htps://example.com` are still handed to the validator untouched and still refused. The one address this reads the wrong way is a scheme of its own that happens to hold an `@`, such as `mailto:me@example.com`: it becomes `https://mailto:me@example.com`, a host with an odd userinfo, where it used to be refused - this field is for web addresses, and no other scheme passes the validator either way.

### Numeric arguments, and what the answers say about them

- **A number outside the range a tool allows is brought into it, and the answer says which** — `depth`, `max_entries`, `timeout_ms`, `offset`, `max_bytes`, `max_results`, `context_lines` and `max_matches_per_file` carry a `minimum` and a `maximum` in the schema, and the MCP SDK enforces neither: a caller asking for more than a tool allows was answered with whatever that tool happened to do about it. What it did was decide in three places that did not agree — two copies of one helper clamped both ends and treated a value that was not an integer as absent, while `search_files` refused a value below the minimum as `INVALID_ARGUMENT` and clamped only the top, so `context_lines: -1` was an error from one tool and `0` from another, and a `timeout_ms` of five minutes came back as two with nothing anywhere saying so. All of them now go through one helper, `boundedInteger`, which clamps both ends and reports what it did; every answer then names the value it used — `timeout_ms`, `offset`, `max_bytes`, `max_entries`, `max_results` — and, when the caller asked for something else, adds one `adjusted:` line naming each argument and what it became. A caller that asked for 500 matches and was given 100 can now tell that apart from a file that has 100. The parameter descriptions say the same, because a schema's bounds are not enforced by every client.

- **`find_files` bounds `max_results` the way every other tool does** — the helper that the other tools share reached `search_files`, `lsp`, `list_directory`, `get_diagnostics` and `run_command`, but not `find_files`, which still refused a value below the minimum as `INVALID_ARGUMENT` while clamping the top with a bare `Math.min` and saying nothing about either end. One argument, asked of two tools that walk the same tree, therefore answered in two different ways: `max_results: 0` was an error from one tool and `1` from the other, and `max_results: 900` came back as 500 with no mention of the limit. It now goes through `boundedInteger` like the rest and carries the same `adjusted:` line, so a caller that asked for more than the tool allows can see that it was answered with less.

- **A number that is not one is answered the way every other tool answers it** — `max_results`, `context_lines` and `max_matches_per_file` are declared `integer` and the SDK does not enforce that either, so `"300000"` reached the tool. `run_command` answered it with the default and said so; the file tools refused it with `INVALID_ARGUMENT`, and `find_files` checked the same argument twice in two places with two different messages. One declared type, two behaviours, and the one a caller was least likely to expect was the error. The file tools now take the same road as the rest: a value that is not an integer falls back to the default and the answer names the number it used.

- **The parameters that were brought into range silently now say so** — `max_bytes`, `get_diagnostics.max_results` and `find_files.max_results` carried no description at all or one that stopped short of the limit, while being clamped like everything else: they were the last three numbers a caller could send out of range and never be told. All three now carry the same sentence the others do, and a test reads every IDE tool's schema so the next bounded number added without it fails the suite. `lsp` `line` and `column` deliberately do not: a position is refused rather than moved, because a line clamped to 1 answers a question about a different line.
- **A value a tool refused is shown the same way everywhere, and cannot break the answer** — the note naming a value that was brought into range built itself with `JSON.stringify`, which throws on a BigInt and on a structure with a cycle in it, so a caller sending either turned an answer about a bad number into an error about describing one. `get_diagnostics` named the severity values it ignored the same way. Both now go through one helper: the value is flattened to a single line, cut short, and quoted, and anything it cannot print at all is named as such instead of thrown. A long or multi-line value used to be able to spend the whole answer on itself; it is now capped at sixty characters.
- **`report_progress` reads a null percentage as no percentage** — a value that is not a number is brought into range from the fallback, which is right for a caller that sent nothing but wrong for one that sent null: an entry with no percentage was shown as "(0%)" on the panel.

### Internal

- **The scope check says what it compares, and a link inside the scope is inside it** — `isWithinSearchScope` folds "." and ".." and nothing else: it never asks the filesystem where a link points, while its comment listed a symlink among the things it catches. Both engines are built on the lexical answer - ripgrep is given no `--follow`, and the fallback walk lists entries `withFileTypes`, where a link is neither a directory to descend into nor a file to read - so nothing behind a link is ever reported. The comment says that now, and says what is left open: a directory replaced by a link between the walk and the read, whose path is still inside as written. Resolving every reported path before judging it was the other way and is not taken: it costs a call per match, it can drop a real match that reaches the scope through a junction on Windows, and it would change an answer nobody has questioned to narrow a race that is still a race afterwards, since a link can move between the resolve and the open.

- **The global git exclude is read once, not once per call** — every `find_files` and `search_files` call read the per-user git config and then the file it names from the beginning, so a walk paid for the same two files again on every call. They are the user's configuration rather than the repository's, so they are read once now and a change to them is picked up when the window is reloaded. The ignore files above the workspace are still read every time: those belong to directories that can change underneath a long-lived window, and a rule that was deleted an hour ago is worse than a read.
- **A message is translated in one language for the whole session** — `translate` read the language setting and rebuilt a translator over the whole catalogue for every message, and the panel and the activity log translate once per entry they show. The language is decided once now, and changing `agentbridge.language` is answered where the configuration change arrives.
- **A glob match has to say which case it means** — `matchesAnyGlob` took a case argument with a default, and two of its four callers wanted the other case: the ignore patterns and the caller's own include and exclude in `search_files` were matched case-sensitively, which is what ripgrep does with them too, but nothing in the call said so. The argument is required now, so a new caller has to choose rather than inherit a guess.
- **A message that is never the same twice no longer piles up** — the throttle that keeps a repeated line from being reported every time keyed its table on the whole message and never dropped an entry, so a line carrying a timestamp or a request id - new text on every appearance - kept one entry apiece for as long as the tunnel ran. The table now holds the last hundred; what falls out is still counted, so a flush reports the repeats it held back instead of losing them.
- **A search for a hunk's lines stops at the second place it matches** — placing a hunk means finding one run of lines, and two possible places already answer `AMBIGUOUS`, so a third cannot change the outcome. The scan collected every position before looking at them, which on an ambiguous needle - one line repeated, or an empty one, which matches at every offset - meant a full pass over the file and an array holding one candidate per line. Uniqueness and absence still cost a whole pass: nothing can be called unique before the end of the file.
- **The two helpers called `boundedText` are named apart** — one bounds the text a panel activity entry shows (`boundedActivityText`), the other what a hover reports to a model (`boundedHoverText`). Neither changed; a search for the shared name used to land on whichever one it found first, and the two answer different readers under different caps.
- **The status getter says which settings it re-reads** — `getStatus` is not a pure read: while the Bridge is stopped it re-reads the tunnel provider and the named-tunnel settings, and drops what was learned about the ones they replace. That is deliberate, because there is no configuration listener, but it was buried in the first lines of a method whose name promises a snapshot. It is its own method now, and the tests pin both halves of the contract: a setting changed while stopped is picked up, and a current error survives being read.
- **One copy of the token estimate and of the concurrency pool the file tools use** — `estimateTokens` was written in `read_files` and again in `search_files`, `mapWithConcurrency` in `find_files` and again in `read_files`: four copies of two answers that have to agree, since a token estimate that differs between tools is a budget one of them cannot keep. Both are in `file-tool-utils.ts` now, with no change to what any caller gets.

## 0.1.9 (2026-09-08)

- **Terminal pool hard cap** — live managed terminals (busy/background included) are capped at 8. When the cap is reached, a command whose cwd matches no idle terminal recycles the least recently used idle one; if every terminal is busy, `run_command` fails fast instead of spawning an unbounded number of terminals.
